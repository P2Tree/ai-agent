# Triage

Move issues through a small state machine of triage roles. Triage only manages **GitHub or GitLab issues and PRs**; it does not manage issue files inside the repository.

If the repo treats external PRs as a request surface, triage covers them too: **a PR is an issue with attached code**, using the same roles and states.

Every comment or issue posted during triage **must** start with:

```
> *This was generated by AI during triage.*
```

## Pre-flight

Detect the tracker from `git remote -v`:

- GitHub → use `gh`
- GitLab → use `glab`
- Neither → stop and tell the user triage only supports GitHub/GitLab.

Commands and default label strings: [tracker commands](references/tracker-commands.md).

Read `GLOSSARY.md` and relevant ADRs if they exist; use the project's terms in notes and briefs. If a decision settles a term or architectural choice, update `GLOSSARY.md`; offer an ADR only when the decision is hard to reverse, surprising without context, and a real trade-off.

## Roles and labels

**Category:** `bug` (something is broken), `enhancement` (new feature or improvement).

**State:** `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`.

These are canonical role names. Map them to the tracker's actual labels at runtime:

1. List existing labels (`gh label list` / `glab label list`).
2. If a label matches the role semantically, reuse its exact string.
3. If none matches, use the default string equal to the role name.
4. Before applying a default that would create a new label, **confirm with the user**.
5. Do not create a per-repo mapping file; resolve labels each session.

For a PR, the states read against the attached code: `ready-for-agent` means a brief is attached and an agent should take the next step; `ready-for-human` means it is ready for a human to merge.

Every triaged issue carries exactly one category and one state. If state roles conflict, flag it and ask the maintainer first.

Transitions: unlabeled → `needs-triage` → `needs-info` / `ready-for-agent` / `ready-for-human` / `wontfix`. `needs-info` returns to `needs-triage` when the reporter replies. The maintainer may override at any time.

## Show What Needs Attention

Query the tracker and present three buckets, oldest first:

1. **Unlabeled** — never triaged.
2. **`needs-triage`** — evaluation in progress.
3. **`needs-info` with reporter activity since the last triage notes** — needs re-evaluation.

When PRs are in scope, include external PRs and tag each line `[PR]` or `[issue]`. Discovery surfaces only external PRs; a collaborator's in-flight PR is not triage work. An explicitly named PR is always triaged.

Show counts and a one-line summary per item. Let the maintainer pick.

## Triage a Specific Issue or PR

1. **Gather context.** Read the full issue or PR (body, comments, labels, author, dates; for a PR, the diff too). Parse prior triage notes. Explore the codebase using the domain glossary and respecting ADRs. Run two checks:
   - **Redundancy:** search for an existing implementation by domain concept, not just wording, and report where you looked. If found, it is an already-implemented `wontfix`.
   - **Prior rejection:** read `.out-of-scope/*.md` if present and surface similar requests.
2. **Recommend.** State category and state with reasoning, plus a brief codebase summary (including whether it already exists). Wait for direction.
3. **Verify the claim.** For a bug, reproduce it from the reporter's steps. For a PR, check out the diff and run the relevant tests or commands. Report: confirmed (with code path), failed, or insufficient detail (a strong `needs-info` signal).
4. **Grill if needed.** Use **grill-me** to flesh out the request a round at a time. As decisions land, update `GLOSSARY.md` and ADRs inline.
5. **Apply the outcome:**
   - `ready-for-agent` → post an agent brief ([guide](references/agent-brief.md)).
   - `ready-for-human` → same structure, but note why it cannot be delegated.
   - `needs-info` → post triage notes (template below).
   - `wontfix`:
     - **Already implemented** — point to where it lives; do not write to `.out-of-scope/`.
     - **Rejected bug** — explain politely, then close.
     - **Rejected enhancement** — write to `.out-of-scope/`, link it from a comment, then close ([guide](references/out-of-scope.md)).
   - `needs-triage` — apply the role; optional comment on partial progress.

## Quick State Override

If the maintainer says "move #42 to ready-for-agent", trust them. Confirm the role change, comment, and close before acting. Skip grilling. If moving to `ready-for-agent` without a grilling session, ask whether they want an agent brief.

## Needs-Info Template

```markdown
## Triage Notes

**What we've established so far:**

- point 1

**What we still need from you (@reporter):**

- question 1
```

Capture everything resolved during grilling under "established so far". Questions must be specific and actionable, not "please provide more info".

## Resuming a Previous Session

If prior triage notes exist, read them, check whether the reporter answered outstanding questions, and present an updated picture. Don't re-ask resolved questions.

## Language Consistency

Match the language of the issue's original body when appending content.
