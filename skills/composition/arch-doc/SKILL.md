# 架构设计说明书编写 Skill

指导如何系统性地为一个代码仓库编写、更新或补充架构设计说明书（Markdown 格式），确保文档准确反映代码实际状态，结构完整，信息有据。

## 核心原则

1. **代码即真相** — 文档中的每一个事实性陈述必须源于对源代码的阅读，而非猜测或记忆。对关键声明（类名、函数签名、数据结构布局），在文档中给出源文件路径以便溯源。如果某个信息无法从代码中确认，标注"待确认"而不是猜测。
2. **先全量阅读，后结构化输出** — 必须先完成对代码库的全量探索，再开始编写文档。不要边读边写，避免信息碎片化。
3. **文档要活** — 架构文档不是一次性产物。当代码变更后，文档应能被高效地更新。为此，文档结构与代码模块结构应保持对齐，并标注关键信息的源文件路径。
4. **具体优于笼统** — 适配方案要明确"用什么替换什么"，差异分析用对比表格，性能/精度目标填实际数值，不留空占位符。

## 输入确认

在开始前，确认以下输入信息（缺失项向用户确认或自行推断并标注）：

| # | 输入 | 是否必需 | 说明 |
|---|------|---------|------|
| 1 | **代码库路径** | 必需 | 本地代码路径，默认为当前工作目录 |
| 2 | **PRD / 需求文档** | 可选 | 产品需求文档，明确功能范围和验收条件；可为文件路径或内联文本 |
| 3 | **SPFS / 功能规格** | 可选 | 软件产品功能规格，列出各特性的支持要求和优先级（P0/P1/P2） |
| 4 | **已有架构文档** | 可选 | 如项目中已有架构文档，阅读并标注差异 |
| 5 | **外部知识库** | 可选 | Confluence / Wiki / 内部文档等，用于交叉验证和补充 |

**PRD 与 SPFS 冲突时**：以 SPFS 为准，冲突条目用脚注标注。若均未提供，基于代码分析推断功能范围和优先级，并标注"推断来源，请确认"。

## 工作流程

```
Task Progress:
- [ ] Step 1: Explore the codebase (read-only)
- [ ] Step 2: Parse PRD/SPFS and external documents
- [ ] Step 3: Load template
- [ ] Step 4: Generate the architecture design document
- [ ] Step 5: Cross-validate and supplement
- [ ] Step 6: Review and output
```

### Step 1: Explore the codebase (read-only)

**必须先完成全部探索，再进入 Step 4 开始编写。**

1. **阅读项目入口文件**：README.md、CLAUDE.md、CMakeLists.txt / Makefile / Cargo.toml / go.mod、构建脚本，理解项目定位、语言、构建方式和外部依赖。
2. **梳理目录结构**：列出顶层目录和关键子目录，理解源码、测试、文档、配置的组织方式。
3. **阅读核心头文件 / 接口定义**：找到主类、主函数、公共 API 的声明，理解系统的对外接口和核心抽象。
4. **追踪核心数据流**：从入口函数出发，追踪主要执行路径，理解数据如何从输入流向输出。
5. **识别关键设计模式**：记录重要的设计模式（Visitor、Factory、CRTP、宏代码生成、插件架构等）及其在代码中的体现。
6. **记录模块间关系**：哪些模块相互依赖，通信方式是什么（函数调用、TCP、管道、共享内存、消息队列等）。
7. **查找已有架构文档**：如果项目中已有架构文档，阅读并标注其中与代码实际状态不符的内容。

**提取要点**：
- 核心功能：系统解决什么问题，关键算法/逻辑
- 目录结构 / 模块划分：各层职责
- 对外 API：主要接口签名和参数
- 硬件/平台依赖：对特定运行时、操作系统、硬件的依赖
- 配置与编译：构建系统、目标平台检测逻辑

### Step 2: Parse PRD/SPFS and external documents

**如果用户提供了 PRD / SPFS**：
- 提取：目标用户场景、功能范围边界（in/out of scope）、非功能需求（性能目标、精度要求、兼容性要求）、各特性优先级（P0/P1/P2）、验收条件

**如果 PRD / SPFS 均未提供**：
- 基于 Step 1 的代码分析推断合理的功能范围和优先级，并在文档中标注

**整理产出**（供后续步骤引用）：

| 特性 | 系统现有能力 | 本次范围 | 优先级 | 验收条件 |
|------|------------|---------|-------|---------|
| {特性名} | {是否支持} | In / Out | P0/P1/P2 | {来自 SPFS 或推断} |

**如果用户要求参考外部知识库**（Confluence / Wiki / 内部文档）：
1. 使用 `confluence-op` skill 或其他可用的文档读取工具获取内容
2. 从外部文档中提取三类信息：
   - **重要补充**：外部文档中有价值但架构文档缺失的信息
   - **矛盾信息**：外部文档与代码不一致的地方（以代码为准）
   - **缺失内容**：外部文档指出但代码和架构文档都未覆盖的已知限制或注意事项
3. 对差异归类：
   - **代码已实现**：纳入文档，标注源文件路径
   - **仅文档声称**：纳入文档但标注"来源为外部文档，未在代码中验证"
   - **矛盾**：以代码为准，标注差异

### Step 3: Load template

读取 [reference/template.md](reference/template.md) 作为文档结构规范。模板定义了 15 个必选章节和可选章节的骨架结构及占位符格式。

### Step 4: Generate the architecture design document

严格按照 template.md 的章节顺序和格式生成文档。内容要求：

#### 必选章节

以下章节为架构设计说明书的标准骨架，每个章节都必须出现（即使某些内容暂时简略）：

| 编号 | 章节 | 核心内容 |
|------|------|---------|
| 1 | 背景和现状 | 项目定位、解决的问题、当前状态、与同类系统的关系、痛点（Observation/Root Cause/Mitigation 三段式） |
| 2 | 设计目标 | 以表格列出，每个目标一句话说明 + 优先级（P0/P1/P2） |
| 3 | 总体结构 | ASCII 架构图 + 分层说明 |
| 4 | 分模块结构 | 每个核心模块一节：职责、关键类/函数、核心数据、源文件路径 |
| 5 | 数据流关系 | 核心数据流的 ASCII 流程图 + 关键路径的文字描述 |
| 6 | 源代码组织结构 | 目录树 + 每个目录/关键文件的用途说明 |
| 7 | 通信 | 模块间/进程间/与外部系统的通信方式和协议（表格） |
| 8 | 关键数据结构 | 核心数据结构的表格（名称、层级、数量/大小、说明） |
| 9 | 异常处理 | 异常分类、传播机制、错误码体系 |
| 10 | 报告输出 | 系统产生的所有输出（trace、日志、统计、比对结果等） |
| 11 | 外部接口 | CLI 参数、库 API、环境变量，以表格列出 |
| 12 | 依赖项说明 | 外部依赖表格（名称、类型、用途、获取方式） |
| 13 | 测试策略 | 测试框架、执行方式、编写规范、覆盖范围、CI 集成 |
| 14 | 影响和限制 | 不支持的功能（表格：特性/说明/支持计划）、性能限制、已知差异 |
| 15 | 术语表 | 术语 / 全称 / 说明 三列表格 |

#### 可选章节

根据项目特征，在章节 14 之后、术语表之前，可增加以下章节：

- 同类系统对比（Simulator vs CModel、Compiler vs Interpreter 等）— 用对比表格逐项列出差异
- 不支持的硬件/平台特性表格 — 包含特性、说明、支持计划三列
- 常见问题排查 — 使用前自查清单 + 常见运行时错误表格
- 安全考量
- 性能特征
- 发布与部署

#### 编写规范

- **架构图用 ASCII art**：使用方框（`┌─┐`）、箭头（`──▶`）、缩进表示层次关系。确保在等宽字体下可读。
- **表格优先**：设计目标、寄存器、内存层次、依赖项、CLI 参数、环境变量、错误码等，一律用 Markdown 表格。同类系统对比用对比表格，不要只用文字描述。
- **标注源文件路径**：在模块标题后标注关键源文件，如 `### 4.1 BirenSimulator（simulator.h/cpp）`。
- **数据流用流程图**：ASCII 流程图展示输入→处理→输出的完整路径，分支用缩进或平行箭头。
- **痛点用三段式**：Observation / Root Cause / Mitigation，参考 template.md 1.3 节格式。
- **不写空话**：每个章节必须有实质内容。如果某个章节暂时无法填充，写"待补充"而不是用空话填充。性能/精度目标填实际数值，不得留空占位符。
- **中文撰写**：技术术语保留英文原文，说明文字用中文。
- **修订历史**：文档开头包含 Revision History 表格，记录每次变更。

### Step 5: Cross-validate and supplement

1. **与现有文档对比**：如果项目中已有 README、设计文档、Confluence 页面等，逐一对比：
   - 现有文档中有但架构文档缺失的重要信息 → 补充
   - 现有文档与代码实际状态矛盾 → 以代码为准，标注差异
   - 现有文档中独有的上下文（如设计决策的历史原因、用户注意事项）→ 吸收到架构文档中
2. **完整性自查**：
   - 所有核心模块是否都有对应章节？
   - 所有外部依赖是否都列出了？
   - 所有关键数据结构是否都覆盖了？
   - CLI 参数和库 API 是否完整？
   - 术语表中是否包含所有在文档中出现过的缩写？
3. **一致性自查**：
   - 同一概念在文档中的命名是否一致？
   - 数据流图与文字描述是否吻合？
   - 章节编号是否连续？

### Step 6: Review and output

输出完整 Markdown 文档，并在结尾给出简短的**风险摘要**（3 条以内最需要关注的风险点或待确认项）。

## 对齐模式（更新已有架构文档）

当用户要求"对齐架构文档"或"根据代码更新架构文档"时，使用以下流程替代 Step 4-6：

1. **先读文档，再读代码**：阅读现有架构文档，列出每个章节中涉及的关键声明（类名、函数签名、配置项、数据结构等）。
2. **逐一验证**：对每个声明，在代码中搜索验证。标注三类差异：
   - **过时**：文档描述的功能在代码中已不存在或已变更
   - **缺失**：代码中有但文档未记录的新功能/模块/接口
   - **矛盾**：文档与代码对同一事物的描述不一致
3. **精准更新**：仅修改有差异的部分，不要重写整个文档。使用 Edit 工具做最小化修改。
4. **新增内容对齐**：如果代码新增了模块或功能，参照文档现有风格补充对应章节。
5. **输出差异报告**：列出所有修改点的摘要，包括章节、修改类型（过时/缺失/矛盾）、具体变更。

## 质量检查清单

完成文档后，逐项检查：

- [ ] 每个模块章节都标注了源文件路径
- [ ] 架构图在等宽字体下可读
- [ ] 所有表格格式正确、列对齐
- [ ] 术语表覆盖了文档中所有缩写
- [ ] 代码中公开的 CLI 参数 / API / 环境变量在文档中完整列出
- [ ] 不支持的功能和已知限制已记录
- [ ] 无空话填充，每个章节有实质内容
- [ ] 性能/精度目标填有实际数值，无空占位符
- [ ] 同类系统对比使用表格，非纯文字描述
- [ ] 修订历史表格已填写
