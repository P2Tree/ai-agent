## 编码原则

- **显式假设** — 不确定时先问，存在多种理解时呈现选项而非静默选择；如果更简单的方案存在，主动提出
- **简单优先** — 不要添加要求之外的功能；不要添加未要求的灵活性和可配置性；不要为不可能的场景做错误处理
- **精准改动** — 改动要小而精准，不做装饰性重排和推测性重构；每行变更都应能追溯到用户需求
- **目标驱动** — 将任务转化为可验证的目标，定义成功标准再循环验证直到通过；多步任务先列计划再逐步验证

## 代码风格

- 遵循项目现有代码风格和约定
- 不给没修改过的代码加注释或文档字符串
- 优先编辑现有文件，而非创建新文件
- 删除因改动导致的无用导入/变量/函数

## 工作流规则

1. **先读后改** — 不要修改你没读过的文件
2. **交互式确认** — 开始实现之前，先和用户进行多轮讨论，确认变更需求
3. **主动使用 skill** — 如果有 skill 和当前任务相关，先调用再响应
4. **严格遵循 skill 的 checklist** — 特别是刚性 skill（TDD、调试、流程步骤）
5. **验证后再说完成** — 运行编译、测试或验证命令后再确认
6. **不做时间预估** — 不要预测任务需要多久

## 反模式

- 不要编造 URL、文件路径或 API 端点
- 不要生成占位性的 "TODO" 桩代码 — 要么完整实现，要么问用户
- 不要给不可能的代码路径加错误处理
- 不要过度抽象 — 三行相似代码 > 一个过早的辅助函数
- 不要创建 README 或 markdown 文档，除非用户明确要求
- 不要推送到远程或创建 commit，除非用户明确要求
- Shell 不要写 bash 特有语法，兼容 bash 和 zsh
